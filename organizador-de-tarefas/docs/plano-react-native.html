Plano de Migração — EchoPlan Web → React Native

Plano completo para portar o organizador de tarefas por voz (React 19 + Vite + Express + Firestore + Gemini) para um app nativo iOS/Android em React Native com Expo. Cobre decisão de stack, tradução de cada API web, roadmap em fases com esforço estimado, riscos e critérios de aceite.

Base analisada: ~11.988 linhas de TS/TSX · src/App.tsx com 2.583 linhas · 29 componentes · server.ts com 537 linhas · Idioma do domínio: pt-BR

1. Sumário executivo

O EchoPlan é hoje uma SPA React que depende fortemente de APIs de browser: MediaRecorder, SpeechRecognition, Notification, Canvas 2D, Blob + <a download>, drag-and-drop HTML5 e Tailwind. Nenhuma dessas existe em React Native. Em compensação, a lógica de domínio — tipos, regras de categoria e prioridade, cálculo de janelas DND, agregações de produtividade, camada Firestore e os prompts do Gemini — é agnóstica de plataforma e migra quase intacta.

Recomendação

Expo (managed) + expo-router + NativeWind v4 + React Native Firebase. Reescrita de UI, reuso do domínio, backend Express preservado como serviço remoto.

Reuso realista

≈ 25–30% do código atual sobrevive quase sem mudança (tipos, hooks de dados, utilitários, servidor). O restante é reescrita de apresentação.

Esforço

9 a 13 semanas para 1 dev sênior full-time até paridade funcional e build de loja. Seis fases, cada uma com entregável testável.

Maior risco

O motor de lembretes. Hoje é um setInterval de 1 s no browser — modelo que não funciona em mobile. Exige reescrita para notificações locais agendadas.

As cinco decisões estruturais

#DecisãoEscolhaRazão
1Framework RNExpo SDK, fluxo managedTodas as capacidades necessárias (áudio, notificações, arquivos, print, share, auth) têm módulo Expo mantido. EAS Build elimina Xcode/Android Studio local no dia a dia.
2Camada Firebase@react-native-firebaseSDK nativo dá persistência offline real do Firestore (o SDK JS não tem em RN) e Google Sign-In nativo. API modular quase idêntica à atual.
3EstiloNativeWind v4Mantém as classes Tailwind já escritas nos 29 componentes. Reduz drasticamente o custo da reescrita de UI frente a StyleSheet puro.
4Lembretesexpo-notifications agendadasÚnico modelo que dispara com o app fechado. Elimina o loop de 1 s que hoje escreve no Firestore a cada tick.
5BackendManter server.ts, publicar remotoOs prompts e responseSchema do Gemini são o ativo de maior valor e não mudam. Muda só o transporte: de same-origin para URL absoluta autenticada.
Ganho colateral

A migração corrige duas dívidas conhecidas do app web: o loop de lembretes que grava no Firestore a cada segundo, e a ausência de persistência offline. Em mobile, nenhuma das duas é opcional — o plano já as trata como escopo.

2. Alternativas avaliadas

Antes de aceitar o custo de uma reescrita de UI, dois caminhos mais baratos foram considerados:

PWA — manifest + service worker ~1 semana Instalável, offline básico, notificação no Android Parcial — iOS não dá notificação local confiável em PWA nem acesso estável ao microfone. Falha justamente no núcleo do produto.
Capacitor — empacota a web app atual ~2–3 semanas App nas lojas reusando ~100% do código Viável — herda a UX de WebView: scroll, teclado, gestos e performance de lista percebidos como não-nativos. Bom plano B se o prazo apertar.

Capacitor entrega app de loja em ~3 semanas reusando o código atual. Este plano continua válido como evolução: a Fase 1 (extração do domínio) beneficia os dois caminhos e pode ser executada antes de a decisão ser tomada.

Armadilha de versão

O projeto usa Tailwind v4 com configuração CSS-first (@theme dentro de src/index.css, sem tailwind.config). NativeWind v4 roda sobre Tailwind 3.4 e exige tailwind.config.js. Traduzir os tokens é trabalho de uma tarde, mas precisa ser feito cedo — todo o restante da UI depende disso.

Classes inexistentes

O código atual espalha classes que não existem (slate-655, indigo-550, slate-850) e que hoje falham em silêncio no browser. Ao portar para NativeWind, essas classes continuam sem gerar estilo, mas o comportamento visual pode divergir do web (onde algum fallback herdado disfarçava). Fazer um grep e normalizar antes da migração de UI.

5. Arquitetura

A arquitetura de três camadas do web se mantém. O que muda é a fronteira entre elas: hoje front e API vivem no mesmo processo e na mesma porta; no mobile, o app é um cliente remoto.

Camada 1 · App nativo
Expo / React Native — iOS e Android

Telas, gestos, gravação de áudio, agendamento de notificações locais, cache offline. Nunca fala com o Gemini diretamente — mesma regra do web.

Camada 2 · Dados
Firestore via @react-native-firebase — fonte de verdade

Mesmas coleções users/{uid}/{tasks,notes,lists}, mesmas regras. Ganha persistência offline nativa: o app abre e funciona sem rede, sincronizando ao reconectar.

Camada 3 · API de IA
server.ts em Cloud Run — API pura

Os quatro endpoints POST /api/tasks/* continuam idênticos. Passa a exigir Authorization: Bearer <Firebase ID token> e a responder CORS, já que deixa de ser same-origin.

Por que o pacote shared paga o próprio custo

O CLAUDE.md do projeto já avisa: "ao mudar categorias ou prioridades, atualize os prompts, o responseSchema e fallbackParseText juntos — eles duplicam a mesma lista". 7. Backend e API

server.ts é a parte mais barata da migração: a lógica de IA não muda em nada. Os quatro endpoints, os prompts em pt-BR, os responseSchema e o parser heurístico fallbackParseText ficam byte a byte iguais. Muda só o entorno.

Segurança — não pular

Hoje a API é pública porque só é alcançável de dentro do applet do AI Studio. Publicada para um app mobile, ela passa a ser um endpoint aberto que gasta cota do Gemini de quem chamar. Verificação de ID token do Firebase é requisito de lançamento, não melhoria futura. Somar rate-limit por uid.

Contrato do cliente HTTP

// apps/mobile/src/lib/api.ts
import auth from '@react-native-firebase/auth';

const BASE = process.env.EXPO_PUBLIC_API_URL; // definido por perfil no eas.json

export async function apiPost<T>(path: string, body: unknown): Promise<T> {
  const token = await auth().currentUser?.getIdToken();
  const res = await fetch(`${BASE}/v1${path}`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
    },
    body: JSON.stringify(body),
  });
  if (!res.ok) throw new Error(await res.text());
  return res.json();
}

Com isso, as seis chamadas fetch("/api/tasks/…") espalhadas em AudioRecorder.tsx, NoteForm.tsx e TaskItem.tsx viram apiPost("/tasks/…") — e o tratamento do fallback isLocalFallback continua igual.

Compatibilidade de dados

O app mobile e o app web vão coexistir na mesma base durante a transição. Isso proíbe qualquer mudança de shape em Task, Note ou List durante a migração. Autenticação

signInWithPopup não existe em RN. O fluxo passa a ser: Google Sign-In nativo devolve um idToken → constrói-se uma credencial → signInWithCredential. O resto do app não percebe a diferença, porque useFirebase continua expondo user via onAuthStateChanged. 

// apps/mobile/src/lib/firebase.ts
import auth from '@react-native-firebase/auth';
import { GoogleSignin } from '@react-native-google-signin/google-signin';

GoogleSignin.configure({ webClientId: '<client id do projeto>' });

export const loginWithGoogle = async () => {
  await GoogleSignin.hasPlayServices();
  const { data } = await GoogleSignin.signIn();
  const credential = auth.GoogleAuthProvider.credential(data.idToken);
  return auth().signInWithCredential(credential);
};

export const logout = async () => {
  await GoogleSignin.signOut();
  await auth().signOut();
};
Preservar

handleFirestoreError() deve continuar relançando o mesmo Error com JSON de diagnóstico (uid, email, path, operação). O formato é esperado pelo tooling do AI Studio e não custa nada manter.

10. Lembretes — a reescrita crítica

Como funciona hoje

App.tsx roda um setInterval de 1 segundo que compara task.reminderTime com o HH:MM atual. A cada tick ele também reseta reminderTriggered no Firestore para tarefas cujo minuto já passou — ou seja, o loop escreve no banco. Três portões de silenciamento se combinam: janela DND, janela de lembretes ativos (com dias da semana) e muteLowPriority.

Por que isso não sobrevive ao mobile

Em iOS e Android, o JavaScript de um app em background é suspenso. O setInterval simplesmente para de rodar quando o usuário sai do app — que é exatamente o momento em que o lembrete precisa disparar. Além disso, um loop de 1 s escrevendo no Firestore drena bateria e cota. Isso não é uma tradução de API; é uma mudança de modelo.

Modelo alvo — agendamento declarativo

Em vez de o app verificar o relógio, ele declara ao sistema operacional quando quer ser acordado. O SO dispara a notificação mesmo com o app fechado.

1. Escrita de tarefacreate / update / delete / toggle
→
2. Reconciliaçãocalcula gatilhos válidos aplicando DND, janela ativa e muteLowPriority
→
3. scheduleNotificationAsync1 agendamento por (tarefa × dia da semana)
→
4. SO disparaapp aberto ou fechado

Onde a reconciliação vive

// apps/mobile/src/lib/notifications.ts
import * as Notifications from 'expo-notifications';

// Chamado após QUALQUER mudança em tasks ou dndSettings.
// Idempotente: apaga tudo e reagenda a partir do estado atual.
export async function reconcileReminders(tasks: Task[], dnd: DndSettings) {
  await Notifications.cancelAllScheduledNotificationsAsync();

  for (const t of tasks) {
    if (!t.reminderTime || t.completed || t.archived) continue;
    if (dnd.muteLowPriority && t.priority === 'Baixa') continue;

    const [hour, minute] = t.reminderTime.split(':').map(Number);
    if (isSilenced(t.reminderTime, dnd)) continue; // reusa a lógica de janela do web

    const days = t.reminderDays?.length ? t.reminderDays : null;
    const content = {
      title: `Lembrete: ${t.title}`,
      body: `Categoria: ${t.category} | Prioridade: ${t.priority}`,
      data: { taskId: t.id },
    };

    if (!days) {
      await Notifications.scheduleNotificationAsync({
        content, trigger: { type: 'daily', hour, minute },
      });
    } else {
      for (const d of days) {
        await Notifications.scheduleNotificationAsync({
          content,
          trigger: { type: 'weekly', weekday: d + 1, hour, minute }, // 0=dom → 1=dom
        });
      }
    }
  }
}
Limite de plataforma

iOS permite no máximo 64 notificações locais agendadas por app. Um usuário com 20 tarefas × 5 dias da semana estoura o limite. Mitigação: agendar apenas a próxima ocorrência de cada tarefa (janela deslizante) e reagendar quando o app abre ou quando uma notificação é entregue. Isso precisa entrar no design desde o começo — não é ajuste posterior.

Recorrência de tarefa continua igual

A recorrência (isRecurring) não tem scheduler hoje: ao concluir uma tarefa recorrente, handleToggleComplete cria uma cópia nova na hora. Esse comportamento migra sem alteração — é lógica de domínio pura. Não confundir com o agendamento de notificações.

11. Áudio e voz

Gravação

Três componentes gravam áudio hoje (AudioRecorder, NoteForm, TaskItem), cada um com sua própria instância de MediaRecorder e lógica de chunks. Na migração, isso vira um hook único useAudioRecorder() usado pelos três — consolidação que o código web nunca fez. 

// Fluxo alvo, com expo-audio
const rec = useAudioRecorder(RecordingPresets.HIGH_QUALITY);
await rec.record();
// … usuário fala …
await rec.stop();
const base64 = await FileSystem.readAsStringAsync(rec.uri, {
  encoding: FileSystem.EncodingType.Base64,
});
await apiPost('/tasks/analyze-audio', { audio: base64, mimeType: 'audio/m4a' });
Formato de áudio

O web envia audio/webm; o mobile envia .m4a (iOS) ou .mp4/.3gp (Android). O Gemini aceita ambos, mas o mimeType passado no inlineData do server.ts precisa vir do cliente em vez de ser fixo. Verificar o valor hardcoded atual antes da Fase 3.

Reconhecimento de fala no dispositivo

O SpeechRecognition do browser é usado hoje para três coisas distintas — e cada uma tem um destino diferente:

Uso atualOndeDestino
Transcrição ao vivo enquanto grava (feedback visual) AudioRecorder.tsx expo-speech-recognition, ou aceitar perder o preview ao vivo e mostrar só o resultado do Gemini
Fallback quando o upload de áudio falha — reenvia o texto capturado para analyze-text AudioRecorder.tsx Requer decisão — sem Web Speech não há texto para reenviar. Alternativa: reter o arquivo e reenviar o áudio quando houver rede
Busca por voz no filtro TaskFilter.tsx expo-speech-recognition ou remover (é conveniência, não núcleo)
Recomendação

Substituir o fallback baseado em Web Speech por uma fila de reenvio offline: se o upload falha, o .m4a fica no FileSystem.documentDirectory e é reenviado quando a conectividade volta. É mais confiável que a transcrição do browser, funciona offline de verdade e aproveita a persistência que o mobile já oferece. Custo: ~meio dia. Ganho: elimina uma dependência de API instável.

O fallback sem Gemini continua valendo

Sem GEMINI_API_KEY, analyze-text cai no parser heurístico local fallbackParseText e responde isLocalFallback: true. Como esse parser vive no servidor e é JS puro, ele funciona igual para o cliente mobile. A UI deve continuar sinalizando o modo degradado ao usuário.

12. Exportações

O app web exporta em quatro formatos. Todos dependem de APIs de browser e todos precisam ser refeitos — mas o resultado no mobile é melhor, porque o share sheet nativo cobre e-mail, nuvem, mensageiros e impressão de uma vez.

ExportMecanismo hojeMecanismo alvoEsforço
Backup JSON Blob + <a download> (lib/backup.ts) FileSystem.writeAsStringAsync → Sharing.shareAsync ~2 h
Histórico CSV String CSV com BOM ﻿ + Blob Mesma geração de string; só troca a entrega. Manter o BOM — é o que faz o Excel abrir os acentos corretamente ~1 h
Relatório semanal PDF jsPDF, layout por coordenadas (WeeklyProgress.tsx) Print.printToFileAsync({ html }) — montar o relatório como HTML string ~1 dia
Planner imprimível PNG Canvas 2D — ~350 linhas de ctx.fillText, gradientes, roundRect Reescrever como HTML+CSS e usar expo-print; ou renderizar uma View oculta e capturar com react-native-view-shot 2–3 dias

Simplificação recomendada

Converter planner e relatório semanal para o mesmo pipeline HTML → expo-print. Uma única função renderReportHtml(data) serve os dois, elimina 350 linhas de Canvas e ~100 de jsPDF, e o resultado é editável por qualquer pessoa que saiba CSS. Custo de reescrita similar, manutenção muito menor.

Backup agendado

O useBackupScheduler hoje faz polling de 1 minuto no localStorage e dispara um banner. Em mobile isso não roda em background. Substituir por uma notificação local agendada ("seu backup está pronto") que, ao ser tocada, abre o app e executa o export. Mesmo padrão da §10.

13. Estilo e tema

Tailwind v4 CSS-first → NativeWind v4

O projeto não tem tailwind.config: os tokens vivem em um bloco @theme dentro de src/index.css, e a variante dark é custom (@variant dark (&:where(.dark, .dark *))) aplicada a uma div raiz — não ao <html>. Nada disso existe no NativeWind.

AspectoHojeAlvo

Dark modeVariante custom + classe dark numa divdarkMode: 'class' + colorScheme do NativeWind

O que não existe em React Native

display: grid, float, position: fixed, z-index com stacking context de CSS, pseudo-elementos (::before), box-shadow com múltiplas sombras, herança de fonte entre componentes, e unidades rem/vh/vw. Cada uso dessas no JSX atual vira um item de trabalho. Todo texto precisa estar dentro de <Text> — não há texto solto dentro de <View>.

Design mobile-first

A UI web é desktop-first com adaptações mobile (sidebar colapsável, menu hambúrguer, drawer de adição). No app, essas construções somem e dão lugar a padrões nativos:

  • Sidebar → bottom tab bar (5 abas) + drawer para configurações e exportações
  • Botão flutuante de adicionar → FAB nativo, com ação longa abrindo a gravação por voz
  • Modais → bottom sheets (@gorhom/bottom-sheet) em vez de overlays centralizados
  • Tooltips → removidos; não há hover em touch. Substituir por rótulos ou ícones autoexplicativos
  • Listas → FlatList com virtualização (o web renderiza tudo de uma vez)
  • Ações de item → swipe actions (concluir / arquivar / excluir) em vez de botões visíveis

16. Roadmap em fases

Seis fases, cada uma com um critério de saída verificável. As fases 1 e 2 são pré-requisito de tudo; da 3 em diante há paralelismo possível se houver mais de um dev.

FASE 1Extrair o domínio~1 semana

Feita no repositório web atual, sem tocar em React Native. Reduz risco e vale mesmo se a migração for cancelada.

  • Criar packages/shared/ com types.ts, dateUtils.ts e um novo domain.ts (categorias, prioridades, mapa de horários vagos).
  • Fazer server.ts e o front importarem a lista única de categorias/prioridades — fecha a duplicação entre prompts, responseSchema e fallbackParseText.
  • Extrair de App.tsx a lógica pura: janelas DND, filtros, agregações de produtividade, regra de recorrência.
  • Escrever testes dessas funções puras — hoje o projeto não tem nenhum teste, e essas são as funções que o app mobile vai reusar sem revisão.
  • Normalizar as classes Tailwind inexistentes (slate-655, indigo-550, slate-850).
Saída: npm run lint passa, app web funciona igual, e existe um pacote de domínio testado e sem dependência de browser.
FASE 2Esqueleto do app + dados~1,5 semana
  • Projeto Expo, expo-router, NativeWind configurado com os tokens traduzidos do @theme.
  • Registrar apps iOS/Android no Firebase; instalar @react-native-firebase.
  • Portar lib/firebase.ts e useFirebase.ts; login Google nativo funcionando.
  • Tela única provisória listando as tarefas do Firestore em tempo real.
  • Publicar server.ts em Cloud Run com verificação de ID token; criar lib/api.ts.
Saída: login real em dispositivo físico, lista de tarefas sincronizando, e um POST /v1/tasks/analyze-text autenticado respondendo.
FASE 3Núcleo do produto — voz e tarefas~2,5 semanas
  • useAudioRecorder com expo-audio; gravação → base64 → analyze-audio.
  • Fila de reenvio offline substituindo o fallback de Web Speech.
  • CRUD completo de tarefas: TaskRow, rota de detalhe, TaskForm, subtarefas, sugestão de subtarefas via IA.
  • Filtros e busca (TaskFilter), reordenação com draggable-flatlist.
  • Bottom tabs com as cinco abas; abas ainda vazias exceto "diárias".
Saída: um usuário consegue falar suas tarefas do dia e vê-las criadas, editadas e concluídas no celular. É o primeiro build que faz sentido mostrar a alguém.
FASE 4Lembretes e notificações~2 semanas

  • Janela deslizante para respeitar o limite de 64 agendamentos do iOS.
  • Portar DND, janela de lembretes ativos e muteLowPriority como filtros de agendamento.
  • Listeners de foreground (ReminderModal) e de toque na notificação (deep link para a tarefa).
  • Soneca, haptics, canal de notificação Android.
  • Fluxo de permissão e tela explicando por que o app precisa notificar.
Saída: lembrete dispara com o app fechado, em iOS e Android, respeitando as três regras de silenciamento. É a fase que precisa de mais teste manual em dispositivo real.
FASE 5Paridade funcional~2,5 semanas

  • Cards de produtividade e gráficos (victory-native).

18. Critérios de aceite

Checklist de paridade funcional. O app só é considerado pronto quando todos passam em dispositivo físico iOS e Android.

Captura

  • Gravar áudio falando várias tarefas e vê-las criadas com título, categoria, prioridade e horário corretos.
  • Horários vagos ("final da tarde") são mapeados conforme a regra do prompt.
  • Criar tarefa por texto livre e por formulário manual.
  • Sem rede: a gravação é enfileirada e enviada ao reconectar.
  • Sem GEMINI_API_KEY: analyze-text cai no parser local e a UI sinaliza o modo degradado.

Lembretes

  • Lembrete dispara com o app fechado, no horário certo.
  • Tocar na notificação abre a tarefa correspondente.
  • Janela DND silencia; janela de lembretes ativos silencia fora dos dias e horas configurados.
  • muteLowPriority silencia tarefas de prioridade "Baixa".
  • Editar o horário de uma tarefa reagenda; concluir ou excluir cancela.
  • Soneca reagenda corretamente.

Dados

  • Uma tarefa criada no app web aparece no mobile em tempo real, e vice-versa.
  • App abre e opera sem rede, sincronizando depois.
  • Categorias, DND, cards visíveis e tema persistem no doc do usuário e valem nos dois clientes.
  • Tarefa recorrente concluída gera a cópia seguinte.

Exportação

  • Backup JSON, CSV do histórico, relatório semanal e planner são gerados e abrem no share sheet.
  • CSV abre no Excel com acentos corretos (BOM preservado).
  • Import de backup restaura tarefas e categorias.

Qualidade

  • Lista com 500 tarefas rola a 60 fps.
  • Dark mode consistente em todas as telas.
  • Alvos de toque ≥ 44 pt; leitor de tela anuncia os controles principais.
  • Nenhuma tela quebra com fonte do sistema ampliada.
  • Textos e mensagens de erro em pt-BR, com acentuação correta.
